# 🔍 debug-socratic

**苏格拉底式调试** — 你贴出代码问「哪里错了」时，Claude 不直接给答案，而是先针对你这份代码里的**具体缺陷**提出 3-5 个引导性问题，逼你自己把 bug 定位出来。

---

## ✨ 为什么要这样

直接拿到答案，修好的是这一个 bug；自己定位出来，练到的是下一批 bug。

这个 skill 刻意堵掉「看出问题 → 说出答案」的最短路径，但**只在有推理空间的时候堵**——拼写错误、包没装这种，问也问不出东西，它会直接告诉你。

---

## 🎯 适用场景

- 刷题 / 写项目时代码跑不通，想自己找出来而不是直接抄修法
- 逻辑 bug、边界条件出错、状态时序问题、并发问题
- 想搞清楚自己的思维盲区在哪，而不只是让代码能跑

---

## 🚫 三种情况它不会提问，直接给答案

| 情况 | 例子 |
|---|---|
| 你明确要答案 | 说「别问了直接说」「在赶时间」 |
| 没有推理空间 | 语法错误、拼写错误、导入路径写错、包没装、版本冲突 |
| 你已经定位了 | 「我知道是这个循环的问题，就是不知道怎么改」 |

---

## 🔑 核心机制

三条设计决定了问题的质量：

**1. 先私下定位，再倒推问题**
Claude 必须先自己把 bug 读出来，再从这个具体成因反推「什么问题能把人引到这」。跳过这步，问出来的一定是撒网式的泛泛题。

**2. 替换测试**
> 把这个问题原样贴到另一个人的代码下面，还成立吗？成立就是泛泛题，删掉。

合格的问题里必须有你代码里的具体东西——变量名、行号、某个输入值、第几轮循环。

- ❌ 你有没有考虑数组为空的情况？
- ✅ 当 `nums` 是 `[]` 时，第 7 行算出来的 `right` 是多少？`while left <= right` 还会进循环吗？

**3. 不许把答案包在问题里**
你只要回答「是/否」就等于拿到答案的，不算问题。

- ❌ 你有没有注意到 `i` 应该从 1 开始？
- ✅ `i = 0` 那一轮，`arr[i-1]` 访问的是哪个元素？

---

## 🔄 回合上限

最多三轮，不会无限提问：

| 回合 | 你的状态 | Claude 做什么 |
|---|---|---|
| 第 1 轮 | —— | 给 3-5 个问题 |
| 第 2 轮 | 定位偏了 | 只针对偏的那一处收窄再问 1-2 个（必须比第一轮更窄） |
| 第 2 轮 | 说不知道 | 先给缩小范围的提示（「只看第 12-15 行」），再问一次 |
| 第 3 轮 | 仍未定位 | 直接讲清楚，并复盘「从哪个信号本来可以看出来」 |

定位对了之后，它还会补两件事：你没注意到的**次生问题**，以及这类 bug 的**模式命名**（下次在什么信号下该警觉）。

---

## 🚀 安装使用

1. 下载 [`debug-socratic.skill`](./debug-socratic.skill)
2. 在 Claude.ai 的 Settings → Capabilities → Skills 中上传
3. 直接贴代码问「哪里错了」即可触发

**触发关键词**：哪里错了 / 为什么跑不通 / 帮我看看这段代码 / 这个 bug 怎么回事 / 输出不对

**跳过提问**：说「别问了直接说」

## 📌 已知边界

- **不适合超长代码**：贴一整个文件（几百行）时，「先私下定位」这一步会不可靠，问题质量下降。建议贴出你怀疑的那个函数
- **不适合性能问题**：「为什么这么慢」需要 profiling 数据而不是逻辑推演，本 skill 帮不上
- **和算法类 skill 的分工**：调试已有代码用本 skill；从零学一道算法题用 [`algo-deconstruct-engine`](../algo-deconstruct-engine/)

# 项目导读

把一个项目讲给没参与过的人。产出是一份导读：读者从头读到尾之后，能说清项目做什么、核心机制怎么运转、为什么这样设计，并且知道每块代码在哪。

导读的目标是理解，不是覆盖。一份把每个目录都介绍一遍的文档，读者读完仍然不知道项目是怎么回事；一份只讲清主干和两三个关键设计的文档，读者反而能自己看懂剩下的部分。所以全程要做取舍：只讲读者建立整体图景所必需的东西。

## 流程

### 1. 先读懂，再动笔

在写下任何一句讲解之前，先自己把项目弄明白。顺序大致是：

1. 读 README 和入口文件，知道项目自称做什么、从哪里启动。
2. 找到**主干**：一次请求、一次运行或一个循环从头到尾经过的那条路径。几乎每个项目都有一条，其它部分都挂在它上面。
3. 找出两三个**让这个项目成为这个项目的设计**。它们通常是作者花了最多代码去保证的东西，也是讲解的重点。
4. 把项目真的跑起来：编译、跑测试、执行一次典型任务，并保留终端输出。真实输出是后面最好的教学材料。跑不起来时（缺密钥、缺环境），想办法用替身跑通流程（假数据、离线模式、本地模拟服务），并在导读里写明这段输出的来历。
5. 记下新人最可能带着的误解，例如以为项目是用另一种语言写的、以为某个目录是核心而其实是脚本。这些要在开头就纠正。

读的过程中留意“文档怎么说”和“代码怎么做”是否一致，这直接决定下一步。

### 2. 核对每一个要写进去的事实

导读里的每个断言都应该能指到一段代码、一个测试或一次实际运行。读者没有能力分辨真假，写错一处会让他带着错误理解去读整个项目。

- README、注释和提示词里的说法只是线索。以代码为准；两者不一致时，写代码的实际行为，并指出差异。
- 区分**系统保证的**和**只是要求的**。写在提示词、注释、文档里的规则，系统并不强制；用类型、校验、权限、工具集实现的规则才是保证。这个区分往往是一个项目最值得讲的地方，也最容易被照抄 README 的讲解抹平。
- 数字从文件和运行结果里取，不凭印象。
- 没有验证过的内容照写，但要标明没有验证。

### 3. 确定读者和终点

用户通常已经说了读者是谁。没说清楚而又影响取舍时，问一句：读者有什么基础，读完要能做什么（看懂演示、回答别人的提问、还是动手改代码）。

默认假设：读者聪明、愿意读，但不认识这个领域的术语，也不熟悉项目所用的语言。按这个假设，凡是你在读代码时自己造的简称或沿用的内部叫法，都要换成读者能看懂的说法，或者先定义再用。

### 4. 排章节

下面是一个经过验证的顺序。它是一条学习路径，前一节为后一节铺垫，所以章节带编号。按项目实际情况增删，不适用的整节去掉，不要为了凑齐而写。

| 章节 | 要回答的问题 |
|---|---|
| 这是什么 | 一段话说清项目做什么、和读者熟悉的东西有何不同。顺手纠正最可能的误解。 |
| 基础概念 | 读懂后文必须认识的词，通常四到七个。每个词一句定义加一个生活类比。 |
| 主干 | 第 1 步找到的那条路径。配一张图。 |
| 关键设计 | 两三个核心设计，各占一节：它是什么、为什么这样做、代价是什么。 |
| 保证与要求 | 哪些规则由代码强制、哪些只靠约定。用表格列出规则、强制方式、代码位置。 |
| 读懂一次运行 | 一段真实输出，逐行说明每行是谁产生的、意味着什么。 |
| 配套机制 | 安全、存储、配置等支撑性内容，点到为止。 |
| 代码地图 | 按“阅读顺序”而不是字母顺序列出目录和文件，每行指回前面的章节。读者不熟悉该语言时，附一张读这门语言的最小词汇表。 |
| 结果与局限 | 项目实测效果如何，数据能说明什么、不能说明什么，已知问题。 |
| 自己跑一次 | 能照着敲的命令。只写你实际执行过的。 |
| 术语表 | 全文出现过的词，一行一个。 |

### 5. 每一节怎么写

- **先概念，后代码。** 读者要先知道一个东西是什么、为什么存在，再看它在哪个文件。反过来写，读者会迷失在文件名里。
- **一个词只定义一次。** 首次出现时给一句定义和一个类比，之后直接用，并始终用同一个词。类比帮读者挂到已有经验上，但一句就够，不要展开成故事。
- **一个机制配一张图。** 图要画出东西怎么流动、边界在哪、谁能碰什么，箭头上写明传的是什么。只有方框和名字的图不如一句话。图下用一句说明写清这张图要让读者看到什么。
- **颜色只表示一件事。** 全文挑一个维度上色（例如“哪个角色在行动”“属于哪个阶段”），从图、正文标签到运行输出都用同一套颜色。这样读者看到颜色就知道指的是谁。
- **真实输出逐行注释。** 把运行输出和解释并排放，一行输出对应一句说明。读者以后自己运行时看到的就是这些行，这一节等于教他读日志。
- **对比用表格，过程用编号步骤，其余用短段落。**
- **每个机制都挂到具体的文件路径**，让读者知道去哪看代码。
- **讲“为什么”和“代价”。** 只描述“是什么”的讲解读完就忘；说清它解决了什么问题、付出了什么，读者才真正理解设计。
- **局限如实写。** 数据不支持的结论不要写，样本小、没验证、有缺陷都直接说。这是读者判断其它内容是否可信的依据。
- **句子短，直接说。** 不铺垫，不用“值得注意的是”一类套话。

### 6. 交付形式

默认产出一个 HTML 页面：可以放图、可以并排注释、可以分享给别人。制作页面前读 `references/page-style.md`，并从 `assets/page-template.html` 开始改，里面有全部组件的样式和示例。所处环境对发布页面另有规定时（例如自带页面骨架或主题约定的发布工具），按那套规定来，保留这里的版式和组件。

用户要 Markdown、文档或幻灯片时，章节规划和写法照旧，只换载体。项目很小、几段话就能讲清时，直接在对话里回答，不必做页面。

### 7. 交付前自查

- 只读第一节的人，知道这个项目是做什么的吗？
- 有没有哪个词在定义之前就用了？
- 每张图是否画出了流动和边界，并配有说明？
- “自己跑一次”里的命令是否都实际执行过？
- 有没有把只是约定的规则写成了系统保证？
- 替身数据、未验证的内容是否都标明了？
- 局限一节是否存在且具体？
- 页面在手机宽度和深色模式下看过一次吗？

## 容易走偏的地方

- **逐目录罗列。** 代码地图只是其中一节，而且放在后面。按目录组织全文，读者得不到主干。
- **复述 README。** README 写给使用者，导读写给想理解的人，两者回答的问题不同。
- **图只有方框和名字。** 见上文：画流动、标箭头。
- **类比喧宾夺主。** 一句类比帮助理解，三段类比变成另一篇文章。
- **省略局限。** 讲解显得更漂亮，但读者拿去回答别人的提问时会出错。

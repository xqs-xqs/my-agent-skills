# project-explainer

把一个代码仓库讲给没参与过、基础薄弱的人。产出一份能从头读到尾的导读，默认是带架构图、逐行注释真实运行输出的 HTML 页面。

## 解决什么问题

让模型"讲讲这个项目"，常见的结果有三种：

- 逐个目录介绍一遍。读完知道每个文件夹叫什么，仍然不知道项目是怎么运转的。
- 复述 README。README 写给使用者，回答的是"怎么用"，不是"为什么这样设计"。
- 把文档和注释里的说法当成事实。比如注释写"这里只接受正数"，代码里却没有检查，传负数照样能跑。讲解照抄注释，读者就会以为这是系统保证的规则，改代码时踩坑。

## skill 做了什么

- **先读懂再动笔**：找到主干（一次运行从头到尾经过的路径）和两三个关键设计，并把项目实际跑一次。跑不起来时用替身数据跑通，并写明输出的来历。
- **每个断言都要能指到代码、测试或一次运行**：文档和代码不一致时以代码为准；区分"系统保证的"和"只是约定的"；没验证的内容标明。
- **按学习路径排章节**：这是什么 → 基础概念 → 主干 → 关键设计 → 保证与约定 → 读懂一次运行 → 代码地图 → 结果与局限 → 自己跑一次 → 术语表。不适用的整节去掉。
- **固定写法**：先概念后代码；一个词只定义一次、配一句类比；一个机制一张图，箭头上标明传的是什么；一种颜色只表示一个维度；局限如实写。
- **交付前自查**：只读第一节的人知道项目做什么吗？命令都执行过吗？有没有把约定写成保证？

## 触发条件

说"帮我理清这个项目""给新人写导读""讲讲这个仓库的架构""onboarding guide"之类，或者要向同事、接手的人、汇报听众解释一个项目时触发。

只问某个函数、某条报错，或者要写 API 文档、安装说明时不触发。

## 为什么讲解流程和页面风格放在同一个 skill 里

两者几乎总是一起用，拆成两个 skill 容易只触发一个。但它们确实是两件事，所以在 skill 内部分开：`SKILL.md` 只写讲解流程，页面风格放在 `references/` 和 `assets/` 里，只有做 HTML 页面时才读。要 Markdown 或幻灯片时，风格部分不会被加载。

## Prompt 版

不支持 skill 的工具里，用 [`prompts/project-explainer.md`](../prompts/project-explainer.md)。它保留了流程和写法，不含页面模板；需要同样的版式时，把 `assets/page-template.html` 一起发给模型。

## 文件

- `SKILL.md`：skill 本体，讲解流程。
- `references/page-style.md`：版式、颜色、字体、组件和画图规则，做 HTML 页面时读。
- `assets/page-template.html`：页面模板，含全部样式和每个组件的占位示例。
- `project-explainer.skill`：打包安装文件。
- `README.md`：本说明，只给人看，不参与触发。

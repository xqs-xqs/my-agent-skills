# cook-from-zero-zh 测试方法

不用一次全做。**优先级：A > B > C > D。** 只做 A，也已经能发现大部分问题。

---

## A. 单盲复现测试（金标准）

**唯一真正的验收标准，其余都是代理指标。** 做一次约 1–2 小时（含做菜）。

**步骤：**

1. 选一道**你从没做过**的菜。建议换烹饪逻辑，别再选煎的——比如糖醋排骨（收汁+糖色）或麻婆豆腐（勾芡+火候）
2. 用 skill 生成指南
3. **全程不查任何其它资料**，照着做
4. 记录三个数：

| 指标 | 目标 |
|---|---|
| 外部查询次数（"这一步到底啥意思"要去搜） | **0** |
| 卡壳次数（"说得不够具体"但你猜着做了） | ≤2 |
| 成品是否达到 L1 声明的水平 | 是 |

**处理方式：每一次外部查询和卡壳，都对应 skill 的一个漏洞。** 记下当时的具体困惑，直接补进 skill。

---

## B. 五个快速测试（各 5–10 分钟，不用真做菜）

生成一份输出，然后对着检查：

| # | 测试 | 做法 | 通过标准 |
|---|---|---|---|
| 1 | **删除测试** | 把所有 `>` 原理块删光 | 剩下的步骤仍能独立做出这道菜 |
| 2 | **分界线测试** | 只读分界线以上 | 完整可执行，且 ≤1200 字 |
| 3 | **约束敏感性** | 改一个约束（"没有烤箱"/"只有电磁炉"）重新生成 | **方案实质改变**，不只是多一句提醒 |
| 4 | **迁移测试** | 读完 A 菜后，让自己或另一个模型预测 B 菜的关键决策 | 能正确预测 ≥2 个 |
| 5 | **压缩测试** | 把全文压成一张 A4 | 压得下，且压完还能照着做 |

**第 3 个最能暴露问题。** 如果换约束后输出几乎不变，说明"约束前置"只是装饰——那是 skill 最容易退化的一环。

**第 4 个直接验证 skill 的立身之本。** 如果原理不能预测新场景，那它只是科普，不是原理。

---

## C. 跨品类压力测试（暴露隐含假设）

用同一份 skill 各生成一份：

- **煎**（牛排）
- **炖**（红烧肉）
- **凉拌**（口水鸡）
- **烘焙**（吐司）

**预期：烘焙会明显失效。** 因为烘焙是"前期精确配比 + 中途不可干预"，而这套 skill 的骨架建立在"感官反馈 + 中途调节"上。

**这不是 bug，是边界。** 结果有两种处理：

1. 写进 SKILL.md 的"何时不用"（v0.1 已预写，用这个测试验证准不准）
2. 或者拆成第二个 skill（`bake-from-zero-zh`）

**能主动画出自己边界的 skill，比号称通吃的可靠得多。**

---

## D. 对照测评（可选）

同一道菜：skill 生成一份 vs 一个高质量外部菜谱（下厨房高分 / Serious Eats）。

找一个不懂做菜的人盲评：**哪份更容易照着做？**

输了说明增量不够。这个测试成本高，但结论最诚实。

---

## 迭代机制：失败驱动的 changelog

每次做失败之后，只问一个问题：

> **是我的执行问题，还是 skill 的表述问题？**

- **执行问题** → 记进参数表，不动 skill
- **表述问题** → 加一条进 skill，**并注明触发它的那次失败**

这一步是整套测试里唯一必须长期坚持的。**没有 changelog 的 skill，说明它没被真正用过。**

格式建议：

```
## Changelog

### v0.2
- 补：焯水前必须说明"冷水下锅还是热水下锅"
  （触发：2026-09-xx 做莲藕排骨汤，热水下锅导致血沫锁在肉里）
```

## 评分卡

跑完 A + B 之后填：

| 项 | 满分 | 得分 |
|---|---|---|
| 外部查询 0 次 | 30 | |
| 卡壳 ≤2 次 | 20 | |
| 删除测试通过 | 15 | |
| 分界线 ≤1200 字且可执行 | 15 | |
| 约束敏感性通过 | 10 | |
| 迁移测试通过 | 10 | |

**≥80 分：可以固定下来长期用。**
**60–80：能用，按扣分项定向修。**
**<60：结构有问题，重写而不是打补丁。**

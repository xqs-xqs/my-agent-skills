# 项目导读提示词（单文件版）

把下面这段贴给任何能读代码的模型使用。它是技能 [`project-explainer`](../project-explainer/) 的压缩版：保留了讲解流程和写法，不含页面模板。需要同样的版式时，把 [`assets/page-template.html`](../project-explainer/assets/page-template.html) 一并提供给模型。

---

请为这个项目写一份导读，读者是【谁，有什么基础】，读完要能【做到什么】。

**先读懂再写。** 读 README 和入口文件；找到主干，也就是一次运行从头到尾经过的那条路径；找出两三个让这个项目与众不同的设计；把项目实际跑一次并保留输出。跑不起来时用替身数据跑通，并在文中写明这段输出的来历。

**核对事实。** 每个断言都要能指到代码、测试或一次实际运行。文档和代码不一致时以代码为准并指出差异。区分“系统强制保证的规则”和“只写在文档或提示词里的约定”。没有验证过的内容要标明。

**按这个顺序组织，不适用的章节去掉：**
1. 这是什么：一段话，并纠正新人最可能的误解。
2. 基础概念：四到七个词，每个一句定义加一句生活类比。
3. 主干：配一张图。
4. 关键设计：每个设计讲清它是什么、为什么这样做、代价是什么。
5. 保证与约定：表格列出规则、强制方式、代码位置。
6. 读懂一次运行：真实输出逐行注释。
7. 配套机制：点到为止。
8. 代码地图：按阅读顺序列目录，每行指回前面的章节；读者不熟悉该语言时附最小词汇表。
9. 结果与局限：数据能说明什么、不能说明什么。
10. 自己跑一次：只写实际执行过的命令。
11. 术语表。

**写法。** 先概念后代码。一个词只定义一次，之后始终用同一个词。一个机制一张图，画出流动和边界，箭头上标明传的是什么，图下用一句话说明这张图要让读者看到什么。全文只用一套颜色表示一个维度（例如哪个角色在行动）。对比用表格，过程用编号步骤。每个机制挂到具体文件路径。局限如实写。句子短，不用套话。

**不要：** 逐目录罗列；复述 README；把约定写成保证；画只有方框和名字的图；把类比展开成故事。

**交付前自查：** 只读第一节的人知道项目做什么吗？有没有词在定义前就用了？命令都执行过吗？替身数据和未验证内容都标明了吗？有局限一节吗？

输出为【一个 HTML 页面 / Markdown 文档】。

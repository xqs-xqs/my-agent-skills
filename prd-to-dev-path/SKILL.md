# 需求文档到开发路径

Agent 写代码很快，一个项目里最慢的环节变成了 Agent 替不了的事：要等日历时间的、只有用户本人能办的、要真用过才知道的。路径按这些来排，代码的先后是次要的。

按顺序做，每步的产出写进里程碑文档。

1. **先列 Agent 替不了的事**：逐条过需求文档，问三个问题，命中任何一个就列出来，第一天启动，和写代码并行。
   - **要等别人或等时间吗？** 要第三方批准、开通、发货、排期的事，代码写得再快也不会提前。
   - **只有用户本人能做吗？** 要用到用户的身份、付款、设备、权限，或者要线下操作。
   - **只有真实环境或真实使用才能回答吗？** 性能、兼容性、数据质量、用户到底会不会这样用。

   每一项写清：谁来做、大概等多久、不成的话退路是什么。

   命中的事因项目而异，要从这份需求文档里找，不要照搬例子。几类项目里常见的：网页应用的域名和服务器，手机应用的商店审核，接第三方接口的密钥和额度，数据项目的数据授权和样本，硬件项目的到货。
2. **第一个里程碑是能用的空壳**：从输入到输出最薄的一条全程，跑在最终要用的真实环境里，由用户亲手用一次，不带业务功能。真实环境里的意外越早暴露，改起来越便宜。
3. **之后每个阶段结束都要能真的用**：按“用户多了一件能做的事”切阶段，一件事从头到尾在同一个阶段里做完。按技术层切（先做完全部底层再做上层）会让用户很晚才能用上。
4. **排先后看两样**：做完难回头的（数据结构、对外接口、选型）先用最小的例子验证再铺开；需求文档里写着“用一段时间再调”的假设，尽早让它被用上。
5. **技术选型每项写三行**：选了什么、放弃了什么、什么情况下这个选择会错。写不出第三行说明还没了解这个选项，先查资料再定。
6. **每个里程碑写清怎么算做完**：一条用户能亲手做的检查，加一条自动测试能证明的事。
7. **标出要用户参与的点**，只有三类：做完难回头的决定、需求文档没写的行为、要用户亲手验证的结果。其余直接做，做完列出来。

交付前自查：第一次能真实使用是在第几个里程碑？默认不超过第 3 个，超过就重排，或者向用户说明为什么排不进去。

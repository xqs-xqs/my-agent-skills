# complex-question-structuring

一次提出大量问题时，让模型先判断用什么结构回答：逐条、整体框架，还是两者混合。

## 解决什么问题

问题一多，模型容易出现两种偏差：

- 把多个小问合并进一个整体框架，有的小问只剩一两句，甚至没有被回答。
- 是非题只答字面（比如只答"没有"），不展开提问者真正关心的原因、利弊和实际意义。

## 为什么做成 skill

如果把"逐条回答"写成默认偏好，模型就失去了判断"这组问题其实该合并"的余地，遇到适合整体框架的场景，回答会变长、变重复。做成通用 skill 后，由模型在每次提问时自己判断该用哪种结构，使用者不需要在不同场景下再额外判断、切换指令。

## 触发条件

一条消息包含 5 个及以上问题时触发。计数包括同一段里的多个问句和句中短语式疑问（如"有什么意义吗""会有影响吗"），不按段落数算，因为一段话里也可能塞了好几个问题。

少于 5 个时不触发：问题少时，每个问题本来就能分到足够篇幅，加载 skill 收益很小，反而可能把本该连贯的解释拆成生硬的几块。

这个阈值是给模型的判断信号，不是严格执行的规则。如果没有自动加载，在问题末尾加一句"按 complex-question-structuring skill 来"即可。

## skill 做了什么

- **先判断**：看每个小问的答案会不会让提问者做出不同的动作或判断，以此决定逐条、框架还是混合。
- **倾向框架的信号**：列出三种更适合整体框架的情况，见下一节。
- **任何结构下都要做到**：三条规则。纠正前提后仍回答原问题；是非题不只答字面；用户明确指定结构时以用户为准。

## 更适合整体框架的三种场景

- **小问都从同一个错误前提长出来。** 纠正一次前提，所有小问一起解决。这时逐条答只会把同一段解释重复几遍。
- **刚进入一个新领域，还不知道该问什么。** 这时候先要一张地图。细节问题等有了框架再问，才问得准。
- **小问之间互相牵制。** 拆开单独答，每个答案各自成立，合起来却可能冲突，需要放在一起权衡。

## 手动指定结构

在问题末尾加一句，直接指定回答结构。它的优先级高于 skill 的自动判断，问题少于 5 个、skill 不触发时同样可用：

- 逐条："逐条答，每个小问都单独展开。"
- 框架："先给整体框架，小问可以合并。"
- 混合："先一两句框架，再逐条答。"
